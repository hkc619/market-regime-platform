# Development Note: Debugging `uvicorn` / `pytest` Startup Hanging

## Date

2026-07-20

## Problem Description

Today, while starting the FastAPI backend with:

```bash
uvicorn app.main:app --reload
```

the terminal only printed one `INFO` line and then appeared to stop. It did not continue to show the usual startup messages.

At the same time, running:

```bash
pytest
```

also produced almost no output, making it look like pytest was hanging as well.

At first, it seemed like the issue might be related to the terminal, `uvicorn`, `pytest`, or FastAPI itself. After debugging, the more likely explanation is:

```text
The application is getting stuck during the Python import phase.
```

In other words, the app was not even reaching the endpoint logic yet. It was already slowed down while Python was importing modules.

---

## Initial Reasoning

When running:

```bash
uvicorn app.main:app --reload
```

Python first needs to execute:

```python
import app.main
```

Then `app.main` imports routers, such as:

```python
from app.api.health import router as health_router
from app.api.predictions import router as prediction_router
from app.api.macro_refresh import router as macro_refresh_router
```

Each router may then import services, repositories, model registries, refresh clients, and other dependencies.

The import chain may look like this:

```text
app.main
  → app.api.predictions
    → app.services.prediction_service
      → app.repository.prediction_repository
      → app.services.data_service
      → app.services.model_registry

  → app.api.macro_refresh
    → app.services.data_refresh_service
      → FRED / yfinance / pandas / SQLAlchemy / config
```

If any module performs heavy work during import time, such as loading a model, reading a large file, querying the database, or calling an external API, both `uvicorn` and `pytest` can appear to hang.

## Issues Checked During Debugging

### 1. Checked whether this was a `Depends(get_db)` issue

A previous error was:

```text
AttributeError: 'Depends' object has no attribute 'execute'
```

The cause was using:

```python
db: Session = Depends(get_db)
```

inside a normal service function and then calling that function directly.

Conclusion:

* `Depends(get_db)` is only resolved by FastAPI inside routes or dependency chains.
* Service functions should receive a real `db: Session`.
* When testing a service directly, use `SessionLocal()` or manually extract a session with `next(get_db())`.

This was not the root cause of today’s `uvicorn` / `pytest` hanging, but it clarified the dependency injection logic.

---

### 2. Checked whether this was a `request.state.request_id` issue

A previous error was:

```text
KeyError: 'request_id'
```

The cause was that some code tried to read:

```python
request.state.request_id
```

before the middleware had assigned it.

The middleware order should ensure:

```python
request.state.request_id = request_id
response = await call_next(request)
```

The `request_id` must be set before `call_next(request)`.

This was also not the main cause of today’s hanging issue, but it helped confirm the request middleware logic.

---

### 3. Checked Pydantic Settings

A previous error was:

```text
fred_api_key
Extra inputs are not permitted
```

The cause was that `.env` contained:

```env
FRED_API_KEY=...
```

but the `Settings` class did not define:

```python
fred_api_key: str | None = None
```

or did not allow extra fields.

A better settings structure is:

```python
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    database_url: str
    fred_api_key: str | None = None

    model_config = SettingsConfigDict(
        env_file=".env",
        extra="ignore",
    )
```

This was not directly causing the startup hang, but config loading is part of the import chain and should remain lightweight.

---

### 4. Checked SQLAlchemy imports

The traceback once stopped around:

```python
from sqlalchemy.orm import Session
```

However, testing SQLAlchemy directly was fast:

```bash
python -c "import sqlalchemy; print(sqlalchemy.__version__)"
python -c "from sqlalchemy.orm import Session; print('sqlalchemy orm ok')"
```

Conclusion:

```text
SQLAlchemy itself was not the cause.
```

The traceback likely stopped there only because `Ctrl+C` was pressed while Python happened to be inside that import stack.

---

### 5. Checked PyTorch imports

Another traceback showed the app entering:

```python
import torch
```

This suggested that `app.main` may have imported `model_registry`, which then imported `torch` at module level.

Potential issue:

```text
FastAPI startup was importing PyTorch before it was actually needed.
```

Suggested fix:

Use lazy import inside the model loading function:

```python
def load_cnn_gru_model(model_path: str):
    import torch

    model = ...
    state_dict = torch.load(model_path, map_location="cpu")
    ...
```

General rule:

```text
Do not import or load PyTorch models during application import time.
```

## Debugging Methods Used

### Method 1: Test app import directly

```bash
python -c "import app.main; print('app import ok')"
```

Purpose:

This helps determine whether the issue happens during:

```text
import app.main
```

or during:

```text
uvicorn startup / lifespan execution
```

If `app import ok` is never printed, the problem is likely in the import phase.

---

### Method 2: Test router imports one by one

```bash
python -c "from app.api.health import router; print('health ok')"
python -c "from app.api.predictions import router; print('predictions ok')"
python -c "from app.api.macro_refresh import router; print('macro refresh ok')"
```

Purpose:

This helps identify which router import chain causes the slowdown.

At first, `predictions` seemed suspicious because it did not print `ok`. Later, `importtime` showed that `prediction_service` itself was not actually slow.

---

### Method 3: Add temporary debug prints between imports

Inside files such as `predictions.py` or `macro_refresh.py`, temporary prints were added:

```python
print("import start")

from fastapi import APIRouter
print("fastapi ok")

from app.services.prediction_service import ...
print("prediction_service ok")

router = APIRouter()
print("router ok")
```

Purpose:

This helps identify the exact import line after which Python stops progressing.

This method is simple and effective, although it requires manually adding and removing debug prints.

---

### Method 4: Use `python -X importtime`

Example commands:

```bash
python -X importtime -c "from app.api.predictions import router" 2> importtime.log
```

or:

```bash
python -X importtime -c "import app.main" 2> importtime.log
```

Purpose:

This measures how long each module import takes.

The output format is:

```text
import time: self | cumulative | module
```

Where:

* `self`: time spent importing the module’s own body
* `cumulative`: total time including all dependencies imported by that module
* unit: microseconds

Conversion:

```text
100,000 μs = 0.1 seconds
1,000,000 μs = 1 second
5,000,000 μs = 5 seconds
```

Rule of thumb:

```text
< 500,000 μs       usually acceptable
> 1,000,000 μs     worth checking
> 3,000,000 μs     suspicious
> 5,000,000 μs     should likely be fixed
> 10,000,000 μs    very likely part of the startup issue
```

## Important Findings

### `prediction_service` was not the main issue

The import timing showed:

```text
import time:       333 |     265562 |   app.repository.prediction_repository
import time:      2557 |     303845 | app.services.prediction_service
```

This means:

```text
303,845 μs ≈ 0.304 seconds
```

So `prediction_service` imported successfully and was not slow enough to explain the hanging behavior.

Conclusion:

```text
prediction_service was not the main root cause.
```

---

### `data_refresh_service` was also not too slow by itself

The import timing showed:

```text
import time:       292 |     413446 |     app.services.data_refresh_service
```

This means:

```text
413,446 μs ≈ 0.413 seconds
```

This is acceptable.

Conclusion:

```text
data_refresh_service alone was not the main issue.
```

---

### `app.api.macro_refresh` was highly suspicious

The import timing showed:

```text
import time:      3125 |   26292427 |   app.api.macro_refresh
```

This means:

```text
26,292,427 μs ≈ 26.29 seconds
```

This is very abnormal for an API router import.

The first number was small:

```text
3125 μs ≈ 0.003 seconds
```

This means the body of `macro_refresh.py` itself was not slow.

However, the cumulative time was large:

```text
26.29 seconds
```

That means:

```text
The dependencies imported through app.api.macro_refresh took a very long time.
```

Conclusion:

```text
The most suspicious import chain is app.api.macro_refresh.
```

---

## Hypothesis

`macro_refresh.py` may be importing a heavy service at module level, such as:

```python
from app.services.data_refresh_service import ...
```

That service or its dependencies may then import:

```python
pandas
yfinance
fredapi
SQLAlchemy
external API clients
config
```

A worse case would be if some module performs work at import time:

```python
settings = get_settings()
fred_client = FredClient(settings.fred_api_key)

refresh_macro_daily()
```

This would cause:

```text
uvicorn startup to run macro refresh logic before the app is ready
pytest collection to run macro refresh logic before tests even start
```

That would explain why both `uvicorn` and `pytest` appeared to hang.

## Attempted / Suggested Fixes

### 1. Temporarily disable the `macro_refresh` router

In `app/main.py`, temporarily comment out:

```python
# from app.api.macro_refresh import router as macro_refresh_router
# app.include_router(macro_refresh_router)
```

Then test:

```bash
python -c "import app.main; print('app import ok')"
```

If this becomes fast, then the issue is likely confirmed to come from:

```text
app.api.macro_refresh
```

---

### 2. Move heavy service imports into endpoint functions

Instead of importing the refresh service at the top of the router file:

```python
from app.services.data_refresh_service import refresh_macro_daily

@router.post("/macro/daily/refresh")
def refresh_daily_macro(db: Session = Depends(get_db)):
    return refresh_macro_daily(db)
```

Use lazy import:

```python
@router.post("/macro/daily/refresh")
def refresh_daily_macro(db: Session = Depends(get_db)):
    from app.services.data_refresh_service import refresh_macro_daily

    return refresh_macro_daily(db)
```

Benefit:

```text
uvicorn startup becomes faster
pytest collection is not slowed down by macro refresh dependencies
health checks and docs are not affected by refresh-specific imports
```

---

### 3. Check for top-level side effects in service modules

Files to check:

```text
app/api/macro_refresh.py
app/services/data_refresh_service.py
app/services/fred_client.py
app/core/config.py
```

Avoid top-level code such as:

```python
db = SessionLocal()
client = FredClient(...)
result = refresh_macro_daily()
df = pd.read_excel(...)
model = load_model()
```

At module level, prefer only:

```python
import ...
class ...
def ...
router = APIRouter()
```

Heavy work should be placed inside:

```python
endpoint functions
service functions
lifespan startup
if __name__ == "__main__"
```

---

### 4. Wrap local test code with `if __name__ == "__main__"`

Avoid:

```python
rows = get_latest_ticker_window("SPY")
print(rows)
```

Use:

```python
if __name__ == "__main__":
    rows = get_latest_ticker_window("SPY")
    print(rows)
```

This prevents local testing code from running when the file is imported by `uvicorn` or `pytest`.

## Key Lessons Learned

### 1. Both `uvicorn` and `pytest` import the app

`uvicorn app.main:app` imports `app.main`.

`pytest` may also import `app.main` during collection through `conftest.py` or test files.

Therefore, if the `app.main` import chain is slow or blocked, both tools may appear to hang.

---

### 2. A traceback location is not always the root cause

At first, it looked like the issue was related to:

```text
prediction_service
```

However, `importtime` showed that `prediction_service` took only about 0.304 seconds.

The real issue appeared more likely to be another router import chain:

```text
app.api.macro_refresh
```

So it is important to use `importtime` or isolated import tests rather than relying only on where the traceback stops.

---

### 3. Avoid heavy work during import time

Main rule:

```text
Imports should define things, not execute heavy work.
```

Do not do the following at module top level:

```text
load model
query database
fetch external API
refresh data
read large files
run prediction
train model
```

---

### 4. `cumulative time` is often more important than `self time`

Example:

```text
import time:      3125 |   26292427 |   app.api.macro_refresh
```

The `self time` is tiny, but the `cumulative time` is huge.

That means the file itself is not slow, but the dependencies imported through that file are expensive.

## Summary

Today’s issue was not caused by `uvicorn` or `pytest` being broken.

The actual issue was likely:

```text
The FastAPI app was importing a heavy module chain during startup.
```

The most suspicious module was:

```text
app.api.macro_refresh
```

because its import cumulative time was around 26 seconds.

The fix direction is:

```text
Reduce heavy top-level imports in routers
Avoid DB / API / model / refresh logic during module import
Use lazy imports where appropriate
Keep import-time behavior lightweight
```
