# 2026-09-08 — Project Completion Roadmap

> Planning date: 2026-09-08; document created: 2026-09-09.
> Goal: Complete Market Regime Platform as a reproducible, demonstrable project supported by tests, with enough depth for a resume and technical interviews.
> The checklist below describes future work, not completed functionality.

## 1. Project Scope and Definition of Done

The first release focuses on SPY market regime classification, with data refresh, model inference, prediction history, historical classification replay, and a usable frontend.

Core demonstration flow:

```text
Start Docker Compose
  → Initialize the database and load demo data
  → Check service, model, and data status
  → Refresh market and macro data (when external connections are configured)
  → Generate and save the latest prediction
  → View probabilities, dates, and prediction history in the frontend
  → Run historical classification replay for a selected date range
```

First-release completion criteria:

- [ ] A new user can start the project in a clean environment by following the README, without editing personal absolute paths.
- [ ] The backend, PostgreSQL, and frontend can start through Compose.
- [ ] Demo mode does not depend on live market data or private API keys; live refresh mode has separate, clear configuration instructions.
- [ ] The core workflow is accessible through the UI, with explicit success, empty-data, and failure states.
- [ ] Automated tests cover units, APIs, real PostgreSQL integration, and browser end-to-end workflows.
- [ ] CI reproduces the main checks; known limitations and validation results are documented.
- [ ] An architecture diagram, screenshots or a short video, and a demo that takes no more than five minutes are available.

## 3. Phase 1 — Make the Core Backend Workflow Reliable (Highest Priority)

- [ ] Support both ordinary column names and MultiIndex columns in the normalizer; validate missing columns, NaN values, dates, OHLC, and volume.
- [ ] Connect data validation to the actual refresh workflow and ensure failures do not leave partial writes.
- [ ] Standardize market and macro refresh responses and logs for success/no_new_data/up_to_date/failed; ensure every branch matches its response schema.
- [ ] Fix the monthly refresh latest_after query and empty-result handling.
- [ ] Use shared service exceptions: insufficient feature data should use the shared AppError hierarchy, and known error classifications should be preserved.
- [ ] Classify timeouts, connection failures, and upstream response errors at the external request boundary.
- [ ] Save the version of the model actually loaded; verify the checkpoint, scaler, feature order, and dimensions.
- [ ] Fix data access and response contracts for supported-assets/model-info.
- [ ] Ensure data readiness accounts for supporting assets, macro data, missing values, and freshness, rather than only counting SPY rows.

### Historical Classification Replay

- [ ] Fix window boundaries: each as_of_date must include that day's row and the preceding 311 trading observations.
- [ ] Align primary and supporting assets by date to prevent positional slicing from shifting windows when data is missing.
- [ ] Fix CPI filling when month-end is not a trading day, preserving the most recent available observation before the window starts.
- [ ] Fix the service/repository argument contract for queries at a specified date.
- [ ] Define behavior and skip reasons for insufficient data, no candidate dates, and failure on every candidate date.
- [ ] Verify that replay does not write to the production prediction_history table.
- [ ] Document limitations around macro observation dates, release times, and revised data vintages; filtering by observation date alone does not establish the absence of look-ahead bias.

**Acceptance criteria:** Refresh, predict, save, and query successfully against a dedicated test database. Replay dates match candidate trading dates, and failure responses can be traced through request IDs.

## 4. Phase 2 — More Comprehensive and Trustworthy Tests

Design tests around risks and behavior. Avoid merely repeating the implementation or using mocks that hide integration errors between layers.

| Level | Main checks | Execution approach |
| --- | --- | --- |
| Unit | Normalization, date windows, missing values, summary statistics, exception classification | Fixed data; no network or database required |
| API contract | Request/response schemas, status codes, empty results, known and unknown errors | TestClient with external dependencies replaced |
| PostgreSQL integration | Real SQL, upserts, transactions, ordering, persistence, and queries | Dedicated test database with fixture setup and cleanup |
| Inference integration | Real preprocessing, scaler, model, output, and version contracts | Fixed data and a fixed model artifact |
| Frontend | Loading, empty, and error states; forms and chart data mapping | Component tests and API fixtures |
| Browser E2E | Generate predictions, query history, and run replay through the UI | Frontend, backend, and test database running together |
| External smoke | Current Yahoo/FRED connectivity and provider contracts | Manual or scheduled; does not block ordinary offline tests |

Tasks:

- [ ] Inventory all existing tests; fix known failures, incorrect mock targets, and empty tests containing only pass.
- [ ] Separate lightweight API fixtures from full-model fixtures in conftest so that every test does not initialize the full application.
- [ ] Prevent unit/API tests from accidentally accessing the production database or external network.
- [ ] Explicitly configure TEST_DATABASE_URL and verify isolation for integration tests; never use the ordinary development database for destructive cleanup.
- [ ] Verify that repeated upserts do not create duplicates, and validate rollback and refresh-log behavior on failure.
- [ ] Cover weekends, holidays, a missing trading day, insufficient windows, non-trading month-end dates, and date-range boundaries.
- [ ] Verify that probabilities are finite, fall within 0–1, sum to approximately 1, and agree with class/regime/confidence.
- [ ] Include at least one API test path through the real service; execute real SQL in repository integration tests.
- [ ] Add test dependencies and execution commands to dependency management and the README; register unit/integration/slow/external markers.
- [ ] Generate coverage reports, inspect uncovered critical branches first, and then establish a baseline; coverage numbers do not replace correctness.
- [ ] Add CI for syntax/lint checks, fast tests, and PostgreSQL integration tests; add builds/E2E after Docker and the frontend are ready.

**Acceptance criteria:** Results are reproducible in a clean environment. All tests required for the first release pass, and external connectivity tests run separately with clear labels.

## 8. Extensions After the First Release

The following are not prerequisites for completing the first release:

- Multi-asset models and batch prediction.
- Scheduled refreshes, background job queues, model switching, and monitoring.
- Full trading-strategy backtesting: trading rules, execution timing, costs, slippage, returns, maximum drawdown, and benchmarks.
- Automated training and model release workflows.

The current backtest's class distribution and confidence summary describe historical classification replay and cannot directly establish trading-strategy performance. Define separate data and evaluation contracts when adding trading backtests.

## 9. Implementation Order and Working Principles

1. Fix the provider/normalizer and complete latest prediction, persistence, and history queries.
2. Fix windows and data alignment while adding tests that exercise real interactions between layers.
3. Establish the full test baseline, database migrations, consolidated configuration, and Docker for the backend + database.
4. Finalize the API contracts needed by the UI and complete frontend/Compose integration.
5. Run browser E2E tests, review model evaluation, and prepare documentation and the demo.

Build tests alongside each phase's functionality instead of waiting until the frontend is complete. Keep each change in a narrowly scoped branch and record its validation method and results. Mark items complete only after their acceptance criteria have been met. Track known failures, unverified workflows, and unimplemented plans separately.
